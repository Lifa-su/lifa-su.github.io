Sitemap Strategies for JavaScript SPAs and Dynamic Websites

Published: February 23, 2026 · 8 min read · AI Sitemap Generator

Single-page applications built with React, Vue, or Next.js deliver fast, app-like experiences — but they create a blind spot for search engines. When your entire site renders inside a single <div id="root">, Googlebot sees an empty shell until JavaScript executes. A well-crafted sitemap becomes the map that guides crawlers through content they might otherwise miss entirely.

If you need a refresher on XML sitemap fundamentals, see our guide on XML sitemap structure and best practices. For broader indexing strategy, check out website indexing strategies for 2026. This article focuses specifically on the challenges JavaScript SPAs and dynamic architectures introduce — and how to solve them.

Why SPAs Break Traditional Sitemap Assumptions

Traditional websites serve fully rendered HTML for every URL. Crawlers request a page, parse the HTML, extract links, and move on. SPAs flip this model: the server returns a minimal HTML document, and client-side JavaScript builds the DOM after load. This creates several sitemap-specific problems:

  • Routes exist only in JavaScript router configuration — there are no physical HTML files to discover
  • Dynamic routes like /products/:id or /blog/:slug generate thousands of URLs that aren't visible until data loads
  • Hash-based routing (/#/about) is invisible to crawlers that don't execute JavaScript
  • Content behind authentication or user interactions may never get indexed

Without a sitemap, you're relying entirely on Google's rendering pipeline to discover your SPA routes — a process that's slower, less reliable, and subject to a limited rendering budget.

Google's Rendering Budget and Delayed Indexing

Google crawls in two waves. The first wave fetches raw HTML and indexes whatever content is immediately available. The second wave renders JavaScript — but this happens later, sometimes days or weeks after the initial crawl. Google allocates a finite rendering budget per site, meaning not every page gets rendered promptly.

For a client-side rendered SPA, this means your content sits in a queue waiting to be rendered before it can be indexed. A sitemap doesn't fix the rendering delay, but it ensures Google knows every URL exists and prioritizes crawling them. Pair your sitemap with proper robots.txt configuration to avoid wasting crawl budget on non-essential routes.

React Apps: Generating Sitemaps from React Router

React applications using react-router define routes in JavaScript, not on the filesystem. To generate a sitemap, you need to extract those routes programmatically. Here's a Node.js script that builds a sitemap from your route configuration:

// scripts/generate-sitemap.js
const fs = require('fs');

const routes = [
  { path: '/', priority: '1.0', changefreq: 'daily' },
  { path: '/features', priority: '0.8', changefreq: 'weekly' },
  { path: '/pricing', priority: '0.8', changefreq: 'weekly' },
  { path: '/docs', priority: '0.7', changefreq: 'weekly' },
  { path: '/blog', priority: '0.9', changefreq: 'daily' },
];

const BASE_URL = 'https://example.com';
const today = new Date().toISOString().split('T')[0];

const xml = `<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
${routes.map(r => `  <url>
    <loc>${BASE_URL}${r.path}</loc>
    <lastmod>${today}</lastmod>
    <changefreq>${r.changefreq}</changefreq>
    <priority>${r.priority}</priority>
  </url>`).join('\n')}
</urlset>`;

fs.writeFileSync('public/sitemap.xml', xml);
console.log(`Sitemap generated: ${routes.length} URLs`);

For dynamic routes like blog posts or product pages, fetch the data from your API at build time and inject those URLs into the sitemap. This is where the real power of dynamic sitemap generation comes in — your sitemap stays in sync with your content.

Next.js: Built-In Sitemap Support

App Router (next-sitemap or Route Handler)

Next.js makes dynamic sitemap generation straightforward. With the App Router, you can create a sitemap.ts file that generates your sitemap at request time or build time:

// app/sitemap.ts
import { MetadataRoute } from 'next';

export default async function sitemap(): Promise<MetadataRoute.Sitemap> {
  const posts = await fetch('https://api.example.com/posts')
    .then(res => res.json());

  const blogUrls = posts.map((post: any) => ({
    url: `https://example.com/blog/${post.slug}`,
    lastModified: new Date(post.updatedAt),
    changeFrequency: 'weekly' as const,
    priority: 0.7,
  }));

  return [
    { url: 'https://example.com', lastModified: new Date(),
      changeFrequency: 'daily', priority: 1.0 },
    ...blogUrls,
  ];
}

For sites with thousands of pages, use generateSitemaps() to split output into multiple sitemap files with an automatic sitemap index. Next.js handles the /sitemap.xml routing automatically — no manual file management needed.

Static Export Considerations

If you're using output: 'export' for static hosting, the dynamic route handler won't work at runtime. Instead, generate the sitemap during next build using a post-build script or the next-sitemap package, which reads your .next build output to discover all generated pages.

Vue and Nuxt: Sitemap Generation Approaches

Vue applications face the same challenges as React SPAs. For standalone Vue apps using vue-router, the approach mirrors the React strategy: extract routes from your router config and generate XML at build time.

Nuxt simplifies this significantly. The @nuxtjs/sitemap module auto-discovers routes from your pages/ directory and generates a sitemap automatically. For dynamic routes powered by API data:

// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['@nuxtjs/sitemap'],
  sitemap: {
    sources: ['/api/__sitemap__/urls'],
  },
})

// server/api/__sitemap__/urls.ts
export default defineSitemapEventHandler(async () => {
  const posts = await $fetch('https://cms.example.com/api/posts');
  return posts.map((p: any) => ({
    loc: `/blog/${p.slug}`,
    lastmod: p.updatedAt,
  }));
})

Headless CMS Sitemap Integration

When your content lives in a headless CMS like Contentful, Strapi, or Sanity, your sitemap must pull from the CMS API to stay current. The pattern is consistent across platforms:

  1. Query the CMS API for all published content entries
  2. Map each entry to its frontend URL using your routing convention
  3. Generate the sitemap XML with accurate lastmod dates from the CMS
  4. Trigger regeneration via webhook when content changes

Most headless CMS platforms support webhooks that fire on publish/unpublish events. Wire these to a serverless function or CI/CD pipeline that regenerates your sitemap immediately when content changes — no stale URLs, no missing pages.

Pre-Rendering vs SSR vs SSG: Impact on Sitemaps

Your rendering strategy directly affects how you approach sitemaps:

  • Client-Side Rendering (CSR): Sitemaps are critical. Without them, crawlers may never discover your routes. Generate at build time from route config + API data.
  • Server-Side Rendering (SSR): Crawlers get full HTML on each request, so link discovery works. Sitemaps still help with priority signals and ensuring deep pages get crawled promptly.
  • Static Site Generation (SSG): Every page exists as a physical HTML file. Sitemaps can be generated directly from the build output. Least complex scenario.
  • Incremental Static Regeneration (ISR): Pages are generated on-demand and cached. Your sitemap should include all possible URLs, even those not yet generated — the first crawl request triggers generation.

Regardless of strategy, add structured data markup to your pages so search engines understand your content's context beyond what the sitemap provides.

Automating Sitemap Updates in CI/CD

Manual sitemap management doesn't scale. Integrate sitemap generation into your deployment pipeline:

# GitHub Actions example
# .github/workflows/deploy.yml
jobs:
  build:
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run build
      - run: node scripts/generate-sitemap.js
      - run: npm run deploy
